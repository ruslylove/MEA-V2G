\chapter{Introduction}

\section{Purpose}
The purpose of this document is to define the software requirements for the MEA-V2G (FreeV2G) project. This system serves as a reference implementation for controlling the 8devices WHITE-beet-EI (EVSE) and WHITE-beet-PI (EV) ISO 15118 modules using an Ethernet host control interface (HCI).

\section{Scope}
The MEA-V2G software encompasses:
\begin{itemize}
    \item Parsing of the protocol used to communicate with the WHITE-beet modules.
    \item Simulation of EVSE and EV behaviors.
    \item Handling of charging parameters (Voltage, Current, Power).
    \item Implementation of basic Control Pilot (CP) and SLAC sequences.
    \item High-level V2G communication management.
    \item Integration with OCPP 2.0.1 for backend communication.
\end{itemize}

\section{Definitions and Acronyms}
\begin{description}
    \item[EV] Electric Vehicle
    \item[EVSE] Electric Vehicle Supply Equipment (Charging Station)
    \item[HCI] Host Control Interface
    \item[SLAC] Signal Level Attenuation Characterization
    \item[V2G] Vehicle-to-Grid
    \item[PNC] Plug \& Charge
    \item[EIM] External Identification Means
    \item[OCPP] Open Charge Point Protocol
    \item[CSMS] Charging Station Management System
\end{description}

\chapter{Overall Description}

\section{Product Perspective}
The software interacts directly with the WHITE-beet hardware modules via Ethernet or SPI. It acts as the "Host" controller, managing the logic while the WHITE-beet module handles the low-level PLC (Power Line Communication) and ISO 15118 framing.

\section{System Functions}
The system enables the following core functions:
\begin{enumerate}
    \item \textbf{Control Pilot (CP) implementation}: Detects EV plugin and manages duty cycles.
    \item \textbf{SLAC}: Automates the matching process between EV and EVSE at the physical layer.
    \item \textbf{V2G Session Management}: Handles Service Discovery, Parameter Discovery, and Authorization.
    \item \textbf{Charging Loop}: Monitoring and control of the active energy transfer.
    \item \textbf{OCPP Communication}: Interface with a CSMS via OCPP 2.0.1 for remote control and status monitoring.
\end{enumerate}

\section{EV State Machine}
The EV internal logic follows a distinct state machine to manage the charging session lifecycle, as observed in the implementation.

\begin{description}
    \item[Init] Initial state where the EV controller is started and hardware interfaces (SPI/Ethernet) are initialized.
    \item[SessionStarted] The V2G session has been established. The EV has successfully matched with the EVSE via SLAC.
    \item[CableCheck] The EV waits for the EVSE to perform the cable check (isolation test) to ensure safety.
    \item[PreCharging] Pre-charge phase where the EV matches its battery voltage to the DC bus voltage.
    \item[Charging] The main state where energy transfer occurs. The EV sends \textit{CurrentDemand} requests in a loop.
    \item[ChargingStopped] The session is terminated, either normally (target SOC reached) or due to an error.
\end{description}

\end{figure}

\section{EVSE State Machine}
The EVSE logic complements the EV, acting as the server component that handles session setup, authorization, and power delivery control.

\begin{description}
    \item[Init] Initialization of the Whitebeet module services (CP, SLAC, V2G).
    \item[Wait] The EVSE waits for an EV to physically plug in (Control Pilot State B).
    \item[SLAC] Signal Level Attenuation Characterization process to pair the EV and EVSE.
    \item[Session] High-level communication session established; protocol negotiation occurs.
    \item[Authorization] Verifying if the EV is authorized to charge (via EIM or Plug \& Charge).
    \item[Params] Exchanging charge parameter limits (Maximum Voltage, Current, Power limits).
    \item[Cable] Performing cable isolation check to ensure no faults exist.
    \item[PreCharge] Adjusting DC output voltage to match the EV's reported battery voltage.
    \item[Charge] Active energy transfer loop responding to the EV's current demand.
    \item[Stop] Session termination and welding detection sequence.
    \item[Faulted] Critical error state (e.g., GFDI trip, Overcurrent). The EVSE opens contactors and sends a \texttt{StatusNotification(Faulted)} to the CSMS via OCPP. It awaits a manual or remote reset.
\end{description}

\section{State Synchronization}
The charging process relies on the tight synchronization between the EV and EVSE states. Figure \ref{fig:staterelation} illustrates the parallel state progression and key synchronization points.

\begin{description}
    \item[Discovery] Control Pilot signal detection (State A $\rightarrow$ B).
    \item[Setup] SLAC matching and V2G Session Setup.
    \item[Safety] Both sides must confirm safety parameters during Cable Check.
    \item[Sync] Voltage levels must be synchronized during Pre-Charge before the contactors close.
    \item[Power] The Charging Loop is a lock-step process where the EV requests and the EVSE delivers.
    \item[Term] Coordinated shutdown to ensure contactors open safely (Welding Detection).
\end{description}

\section{Core Components}
The system comprises the following key software components:

\subsection{Whitebeet Component}
The \texttt{Whitebeet} class serves as the Hardware Abstraction Layer (HAL). It manages the low-level communication with the physical ISO 15118 module via Ethernet or SPI.
\begin{itemize}
    \item \textbf{Packet Framing}: Handles the encapsulation of Host Control Interface (HCI) commands.
    \item \textbf{Event Dispatching}: Receives raw data from the hardware and dispatches events (e.g., \texttt{EV\_CONNECTED}, \texttt{V2G\_MESSAGE}) to the higher-level logic.
    \item \textbf{Service Management}: Exposes methods to control Control Pilot (CP) state, SLAC, and V2G messaging.
\end{itemize}

\subsection{EV Component}
The \texttt{EV} class is the central controller for the client side. It orchestrates the charging session from the vehicle's perspective.
\begin{itemize}
    \item \textbf{State Machine}: Implements the ISO 15118 client flow (Session Setup $\rightarrow$ Charge Parameter Discovery $\rightarrow$ Power Delivery).
    \item \textbf{Hardware Aggregation}: Owning instance of \texttt{Whitebeet} (for comms) and \texttt{Battery} (for energy simulation).
\end{itemize}

\subsection{EVSE Component}
The \texttt{EVSE} class is the central controller for the station side. It manages the server-side logic and power delivery authorization.
\begin{itemize}
    \item \textbf{State Machine}: Implements the ISO 15118 server flow, including Service Discovery and Plug \& Charge authorization.
    \item \textbf{Hardware Aggregation}: Owning instance of \texttt{Whitebeet} (for comms) and \texttt{Charger} (for power delivery simulation).
    \item \textbf{Scheduling}: Manages SASchedules based on configuration.
\end{itemize}

\subsection{OCPP Component}
The system integrates an OCPP 2.0.1 client to enable remote management.
\begin{itemize}
    \item \textbf{OcppInterface}: Adapts the \texttt{ocpp} library's \texttt{ChargePoint} class to the MEA-V2G architecture. It maps OCPP commands (e.g., \texttt{RequestStartTransaction}) to local \texttt{Charger} actions.
    \item \textbf{OcppWorker}: A dedicated thread that manages the \texttt{asyncio} event loop and WebSocket connection to the CSMS, ensuring non-blocking operation alongside the main application loop.
\end{itemize}



\section{Charger Component}
The \texttt{Charger} class performs a physical simulation of the power electronics, ensuring realistic behavior during the charging session. Its key functions include:
\begin{itemize}
    \item \textbf{Output Ramping}: Instead of instantaneous jumps, the charger simulates the physical "slewing" of voltage and current over time. It uses defined $\Delta U$ and $\Delta I$ rates to ramp the output toward the target setpoint.
    \item \textbf{Limit Enforcement}: It strictly enforces hard safety limits for the system (e.g., \texttt{evse\_max\_current}, \texttt{evse\_max\_power}), protecting the modeled hardware.
    \item \textbf{Setpoint Control}: The EV provides dynamic target values (\textit{Target Voltage}, \textit{Target Current}), which the charger attempts to follow within its safety constraints.
    \item \textbf{Fault Detection}: The class includes methods like \texttt{isVoltageLimitExceeded()} and \texttt{isPowerLimitExceeded()} to trigger immediate session termination if operating conditions are violated.
\end{itemize}

The \texttt{Charger} class implements the \texttt{ChargerInterface} abstract base class. This design pattern allows the simulation module to be easily swapped with a real hardware driver, such as the \texttt{CanCharger} class, which communicates with physical power electronics via CAN bus using the \texttt{python-can} library, while maintaining a consistent API for the \texttt{EVSE} logic.

\subsection{Implementing a Custom Charger}
To integrate specific power electronics hardware, developers must create a subclass of \texttt{ChargerInterface}. This ensures the \texttt{EVSE} logic remains decoupled from the physical layer.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\textwidth]{charger_interface_class_diagram.pdf}
    \caption{Charger Interface and Implementation}
    \label{fig:chargerinterface}
\end{figure}

A custom implementation must override the abstract methods to map high-level commands to hardware-specific protocols. The following sections detail the requirements for each group of methods.

\subsubsection{Lifecycle Management}
These methods control the high-level operational state of the power electronics.
\begin{description}
    \item[\texttt{start()}] Called when the EVSE initializes or prepares for a session. It should initialize hardware communication (e.g., open CAN sockets). \textbf{Note}: This method should \textbf{not} automatically close the output contactors; that is handled by the state machine after safe voltage matching.
    \item[\texttt{stop()}] \textbf{Critical Safety Method}. Called to terminate a session or during error conditions. It must immediately disable power output, open contactors, and return the hardware to a safe idle state (0V/0A).
\end{description}

\subsubsection{Control Loop Methods}
These methods are called cyclically (typically every 10-100ms) during the active charging phase.
\begin{description}
    \item[\texttt{setEvTargetVoltage(val)}] Receives the EV's requested voltage setpoint (in Volts). The implementation must transmit this request to the power supply unit (PSU).
    \item[\texttt{setEvTargetCurrent(val)}] Receives the EV's requested current setpoint (in Amps). The implementation must ensure the PSU imposes this current limit.
\end{description}
\textit{Return Value}: These methods must return \texttt{True} if the command was successfully queued or sent to the hardware, and \texttt{False} if the request triggers a local hardware fault or limit violation.

\subsubsection{Telemetry Methods}
The EVSE state machine relies on accurate feedback to perform safety checks (e.g., Welding Detection) and process steps (e.g., Pre-Charge).
\begin{description}
    \item[\texttt{getEvsePresentVoltage()}] Must return the \textit{measured} voltage at the DC output terminals. Do not return the internal setpoint; the actual value is required to verify contactor states.
    \item[\texttt{getEvsePresentCurrent()}] Must return the \textit{measured} current flowing to the EV.
\end{description}

\subsubsection{Configuration Accessors}
The interface includes getters and setters for electrical limits (e.g., \texttt{setEvseMaxCurrent}, \texttt{getEvseMaxPower}).
\begin{itemize}
    \item For a \textbf{Simulation} (like \texttt{Charger.py}), these methods simply store and retrieve variables to emulate different hardware capabilities.
    \item For \textbf{Physical Hardware}, the setters (e.g., `setEvseMaxCurrent`) should theoretically configure the hardware's internal safety latches if supported. The getters must return the valid limits to be advertised to the EV during the \textit{Charge Parameter Discovery} phase.
\end{itemize}


\subsection{TRIO-HP Charger Protocol}
This section details the specific hardware and communication protocol for the TRIO-HP/\allowbreak 3AC/\allowbreak 1KDC/\allowbreak 20KW/\allowbreak BI power module, which is supported by the system via a CAN bus interface.

\subsubsection{Hardware Description}
\begin{itemize}
    \item \textbf{Brand}: PHOENIX CONTACT
    \item \textbf{Model}: TRIO-HP/3AC/1KDC/20KW/BI
    \item \textbf{Function}: Bidirectional DC/AC and AC/DC converter.
    \item \textbf{Communication}: CAN 2.0B Extended Frame (29-bit Identifier).
    \item \textbf{Baud Rate}: 125 kbps.
    \item \textbf{Termination}: 120 $\Omega$ resistors required.
\end{itemize}

\subsubsection{Protocol Structure}
The protocol uses a 29-bit extended identifier structured as follows:

\begin{center}
\begin{tabular}{|c|c|c|c|c|}
\hline
\textbf{Error (3 bits)} & \textbf{Device No. (4 bits)} & \textbf{Command (6 bits)} & \textbf{Target (8 bits)} & \textbf{Source (8 bits)} \\
\hline
28-26 & 25-22 & 21-16 & 15-8 & 7-0 \\
\hline
\end{tabular}
\end{center}

\begin{itemize}
    \item \textbf{Error Code}: 0x00 = Normal.
    \item \textbf{Device No}: 0x0A for individual modules, 0x0B for groups.
    \item \textbf{Target/Source Address}: Unique module ID; Controller default is 0xF0.
\end{itemize}

\subsubsection{Key Commands}
The system utilizes the following CAN commands to control the charger:

\begin{center}
\begin{tabular}{|l|c|c|l|}
\hline
\textbf{Description} & \textbf{Cmd ID} & \textbf{Data Bytes (Hex)} & \textbf{Notes} \\
\hline
Read DC Voltage & 0x23 & 10 01 00 00 ... & Response contains voltage in mV. \\
\hline
Read DC Current & 0x23 & 10 02 00 00 ... & Response contains current in mA. \\
\hline
Set DC Voltage & 0x24 & 10 01 00 00 ... & Sets output voltage target (mV). \\
\hline
Set DC Current & 0x24 & 10 02 00 00 ... & Sets output current limit (mA). \\
\hline
Enable Operation & 0x24 & 11 10 00 00 ... & Byte 7: 0xA0 (On), 0xA1 (Off). \\
\hline
\end{tabular}
\end{center}

\begin{center}
\begin{tabular}{|l|p{4cm}|p{4cm}|p{4cm}|}

\subsubsection{CanCharger Implementation}
The \texttt{CanCharger} class provides the concrete implementation for the TRIO-HP protocol. It utilizes the \texttt{python-can} library to handle low-level bus arbitration and message framing.
\begin{itemize}
    \item \textbf{Bus Abstraction}: Supports multiple interfaces (SocketCAN, Kvaser, Virtual) via the library's abstraction layer.
    \item \textbf{Threaded Listening}: A continuous background thread monitors the bus for broadcast updates (e.g., current system voltage) to keep the internal state synchronized with the hardware.
    \item \textbf{Error Handling}: Automatically detects connection failures or missing libraries, falling back to safe states or raising initialization errors.
\end{itemize}

\section{Battery Component}
The \texttt{Battery} class provides a logical model of the EV's energy storage, managing State of Charge (SOC) and physical limits.
\begin{itemize}
    \item \textbf{Energy Tracking}: Maintains the battery capacity (Wh) and current energy level. SOC is dynamically calculated as $\frac{\textit{Current Level}}{\textit{Capacity}} \times 100$.
    \item \textbf{Charging Process}: The \texttt{tickSimulation()} method accumulates energy over time intervals based on the instantaneous input voltage and current ($E = V \times I \times \Delta t$).
    \item \textbf{Configurable Limits}: Supports defining maximum Voltage, Current, and Power constraints specific to the chosen Energy Transfer Mode (AC vs. DC).
    \item \textbf{Status Reporting}: Continuously updates the SOC and charging status ('is\_full', 'is\_charging'), which are reported back to the EVSE via ISO 15118 messages.
\end{itemize}

\section{Default Charging Routine}
In the absence of an external configuration file, the system defaults to a hardcoded "Simple Charging Routine" defined in \texttt{Application.py}. This routine ensures the EVSE behaves predictably during initial testing or standalone operation.

\subsection{Default Schedule}
The default charging profile is a time-dependent power curve that simulates a decreasing power availability (e.g., grid balancing or solar curve):
\begin{itemize}
    \item \textbf{0 to 30 minutes}: Maximum Power 25,000 W.
    \item \textbf{30 to 60 minutes}: Maximum Power reduced to 18,750 W.
    \item \textbf{Over 60 minutes}: Maximum Power further reduced to 12,500 W.
\end{itemize}

\subsection{Physics Simulation Parameters}
To simulate realistic hardware behavior, the \texttt{Charger} class uses specific delta parameters to ramp voltage and current rather than applying instantaneous steps:
\begin{itemize}
    \item \textbf{Delta Voltage}: 0.5 V per tick.
    \item \textbf{Delta Current}: 0.05 A per tick.
    \item \textbf{Max Limits}: 400 V / 100 A / 25 kW.
\end{itemize}

\section{Functional Requirements}

\subsection{FR-01: Protocol Negotiation}
The system shall support negotiation of ISO 15118 protocol versions.
\begin{itemize}
    \item The EVSE shall advertise supported protocols.
    \item The EV shall select a mutually supported protocol (e.g., DIN SPEC 70121 or ISO 15118-2).
\end{itemize}

\subsection{FR-01-A: OCPP Version Selection}
The system shall allow the selection of the OCPP protocol version at startup.
\begin{itemize}
    \item Supported versions: OCPP 1.6, OCPP 2.0.1, and OCPP 2.1 (experimental).
    \item The version shall be configurable via command-line arguments.
\end{itemize}

\subsection{FR-02: Authorization}
The system shall support multiple authorization modes:
\begin{itemize}
    \item \textbf{EIM (External Identification Means)}: Manual authorization via console input.
    \item \textbf{PnC (Plug \& Charge)}: Automated certificate-based authorization.
\end{itemize}

\subsection{FR-03: Charging Control}
During the charging loop, the system shall:
\begin{itemize}
    \item Exchange charging parameters (SOC, Target Voltage, Target Current).
    \item Terminate the session upon "Stop Charging" request from either side.
\end{itemize}

\subsection{FR-04: OCPP Integration}
The system shall implement OCPP client features for the selected version (1.6, 2.0.1, or 2.1):
\begin{itemize}
    \item Connect to a CSMS via WebSocket.
    \item Send version-specific \texttt{BootNotification} and \texttt{Heartbeat} messages.
    \item Accept remote commands appropriate for the version (e.g., \texttt{RemoteStartTransaction} for 1.6, \texttt{RequestStartTransaction} for 2.0.1+).
    \item Support configuration/variable management (\texttt{ChangeConfiguration} for 1.6, \texttt{SetVariables} for 2.0.1+).
\end{itemize}

\section{OCPP Connector State Machine}
The EVSE maintains a logical state for each connector, which is reported to the CSMS via Status Notification messages. This state machine abstracts the underlying ISO 15118 physical processes.

\begin{description}
    \item[Available] The connector is free and ready for a new session.
    \item[Preparing] An EV is plugged in or an authorization process is pending.
    \item[Charging] Active energy transfer is in progress.
    \item[SuspendedEV] Charging is paused by the EV (e.g., battery full).
    \item[SuspendedEVSE] Charging is paused by the EVSE (e.g., smart charging limit).
    \item[Finishing] The session has stopped, waiting for the plug to be removed.
    \item[Reserved] The connector is reserved for a specific user.
    \item[Unavailable] The connector is operative but not available for use (e.g., maintenance).
    \item[Faulted] A critical error has occurred.
\end{description}

    \centering
    \includegraphics[width=0.9\textwidth]{ocpp_state_diagram.pdf}
    \caption{OCPP Connector Status State Machine}
    \label{fig:ocppstatediagram}
\end{figure}

\subsection{State Transition Logic}
The following table details the communication packets exchanged between the EV, EVSE, and CSMS that trigger the transitions in the OCPP Connector State Machine.

\small
\begin{longtable}{|p{3.0cm}|p{3.5cm}|p{4.5cm}|p{4.5cm}|}
\hline
\textbf{Transition} & \textbf{Physical Trigger} & \textbf{ISO 15118 (EV-EVSE)} & \textbf{OCPP (EVSE-CSMS)} \\
\hline
\multicolumn{4}{|l|}{\textit{Normal Operation}} \\
\hline
Available $\rightarrow$ Preparing & Plug In (CP $A \rightarrow B$) & SLAC Match, SessionSetupReq & StatusNotification(Preparing) \\
\hline
Preparing $\rightarrow$ Charging & Power Delivery Start (CP $B \rightarrow C$) & PowerDeliveryReq(Start), CurrentDemandReq & TransactionEvent(Started), StatusNotification(Charging) \\
\hline
Charging $\rightarrow$ Finishing & Session Stop (CP $C \rightarrow B$) & PowerDeliveryReq(Stop) or SessionStopReq & TransactionEvent(Ended), StatusNotification(Finishing) \\
\hline
Finishing $\rightarrow$ Available & Unplug (CP $B \rightarrow A$) & N/A & StatusNotification(Available) \\
\hline
\multicolumn{4}{|l|}{\textit{Suspended States}} \\
\hline
Charging $\rightarrow$ SuspendedEV & EV pauses (e.g. max SOC) & CurrentDemandReq (Target=0A) & StatusNotification(SuspendedEV) \\
\hline
SuspendedEV $\rightarrow$ Charging & EV resumes & CurrentDemandReq (Target$>$0A) & StatusNotification(Charging) \\
\hline
Charging $\rightarrow$ SuspendedEVSE & EVSE limits power & CurrentDemandRes (MaxCurrent=0A) & StatusNotification(SuspendedEVSE) \\
\hline
SuspendedEVSE $\rightarrow$ Charging & EVSE lifts limit & CurrentDemandRes (MaxCurrent$>$0A) & StatusNotification(Charging) \\
\hline
Suspended $\rightarrow$ Finishing & Stop during pause & SessionStopReq & TransactionEvent(Ended), StatusNotification(Finishing) \\
\hline
\multicolumn{4}{|l|}{\textit{Reservation \& Availability}} \\
\hline
Available $\rightarrow$ Reserved & N/A & N/A & ReserveNowReq, StatusNotification(Reserved) \\
\hline
Reserved $\rightarrow$ Preparing & Plug In + Auth & SessionSetupReq & StatusNotification(Preparing) \\
\hline
Reserved $\rightarrow$ Available & Timeout / Cancel & N/A & CancelReservationReq, StatusNotification(Available) \\
\hline
Available $\rightarrow$ Unavailable & Operator Command & N/A & ChangeAvailabilityReq, StatusNotification(Unavailable) \\
\hline
Unavailable $\rightarrow$ Available & Operator Command & N/A & ChangeAvailabilityReq, StatusNotification(Available) \\
\hline
\multicolumn{4}{|l|}{\textit{Exception Layout}} \\
\hline
Preparing $\rightarrow$ Available & Unplug (Invalid Session) & SessionStopReq & StatusNotification(Available) \\
\hline
Any $\rightarrow$ Faulted & Error / Fault & Welding Detection Fail, etc. & StatusNotification(Faulted) \\
\hline
Faulted $\rightarrow$ Available & Reset / Recovery & N/A & ResetReq, StatusNotification(Available) \\
\hline
Faulted $\rightarrow$ Unavailable & Permanent Fault & N/A & ChangeAvailabilityReq, StatusNotification(Unavailable) \\
\hline
\end{longtable}

\chapter{Configuration and Deployment}

\section{Command Line Interface (CLI)}
The system is launched via \texttt{Application.py} with several arguments to define its operating mode:

\begin{itemize}
    \item \texttt{-r, --role}: Specifies the mode of operation (\texttt{EV} or \texttt{EVSE}).
    \item \texttt{-i, --interface}: Defines the network interface connected to the Whitebeet module (e.g., \texttt{eth0}).
    \item \texttt{-c, --config}: Path to the EV configuration file (default: \texttt{ev.json}).
    \item \texttt{-ec, --evse-config}: Path to the EVSE configuration file (default: \texttt{evse.json}).
    \item \texttt{--auto}: (EVSE only) Enables automatic authorization for Plug \& Charge.

    \item \texttt{--api-port}: Sets the port for the REST API status monitor.
    \item \texttt{--ocpp-url}: (EVSE only) WebSocket URL for the OCPP CSMS.
    \item \texttt{--ocpp-id}: (EVSE only) The Charge Point ID to Identify the station to the CSMS.
    \item \texttt{--ocpp-version}: (EVSE only) The OCPP protocol version to use (\texttt{1.6}, \texttt{2.0.1}, or \texttt{2.1}). Defaults to \texttt{2.0.1}.
\end{itemize}

\section{JSON Configuration}
Behavioral parameters are externalized in JSON files to allow run-time customization without code changes.

\subsection{EV Configuration (ev.json)}
Defines the characteristics of the Electric Vehicle:
\begin{itemize}
    \item \textbf{ev}: Supported protocols (ISO 15118-2, DIN), payment methods (EIM, PnC), and energy transfer modes.
    \item \textbf{battery}: Physical parameters including capacity, maximum voltage/current, and initial SOC.
\end{itemize}

\subsection{EVSE Configuration (evse.json)}
Defines the characteristics of the Charging Station:
\begin{itemize}
    \item \textbf{charger}: Output limits (Max Voltage/Current/Power) and slew rates ($\Delta V, \Delta I$) for the simulation.
    \item \textbf{schedule}: Defines power delivery schedules (SASchedules) sent to the EV during the Charge Parameter Discovery phase.
\end{itemize}

\section{Software Dependencies}
The MEA-V2G software relies on the following external Python libraries for hardware communication and protocol handling:
\begin{itemize}
    \item \textbf{python-can}: Required for the \texttt{CanCharger} class to communicate with CAN-based power modules.
    \item \textbf{spidev}: Required for SPI communication with the Whitebeet module on Raspberry Pi platforms.
    \item \textbf{RPi.GPIO}: Required for General Purpose I/O control on Raspberry Pi.
    \item \textbf{Flask}: Required for the REST API server.
\end{itemize}

\section{Test Procedures}

\subsection{TC-01: System Initialization}
\textbf{Objective}: Verify the application correctly detects and initializes the Whitebeet hardware. \\
\textbf{Steps}:
\begin{enumerate}
    \item Power on the detailed hardware.
    \item Launch `python3 Application.py --role evse`.
    \item Observe console logs for `[Whitebeet] System Version: x.y.z`.
\end{enumerate}
\textbf{Expected Result}: The system reports a valid firmware version and enters the `Wait` state (CP State A).

\subsection{TC-02: EV Connection}
\textbf{Objective}: Verify successful plug-in detection and SLAC matching. \\
\textbf{Steps}:
\begin{enumerate}
    \item Ensure EVSE is in `Wait` state.
    \item Physically connect the CCS cable (simulated by connecting CP/PE pins).
    \item Trigger SLAC from the EV side.
\end{enumerate}
\textbf{Expected Result}:
\begin{itemize}
    \item EVSE transitions to `SLAC`.
    \item Matching is successful (GreenPHY association).
    \item EVSE transitions to `Session` (Protocol Negotiation).
\end{itemize}

\subsection{TC-03: Authorization}
\textbf{Objective}: Verify the system correctly processes payment/authorization methods. \\
\textbf{Steps}:
\begin{enumerate}
    \item Initiate a session with `PaymentOption=ExternalPayment` (EIM).
    \item When prompted on the EVSE console, enter "yes" to authorize.
\end{enumerate}
\textbf{Expected Result}: EVSE transitions from `Authorization` to `Parameter Discovery`.

\subsection{TC-04: Charging Loop}
\textbf{Objective}: Verify the main energy transfer loop. \\
\textbf{Steps}:
\begin{enumerate}
    \item Complete Pre-Charge (Voltage matching).
    \item EV requests a current draw (e.g., 10A).
\end{enumerate}
\textbf{Expected Result}:
\begin{itemize}
    \item Contactors close (Simulated).
    \item EVSE output current ramps to 10A.
    \item `CurrentDemandRes` messages return `DC\_EVSEStatus=Charging`.
\end{itemize}

\subsection{TC-05: Session Stop}
\textbf{Objective}: Verify normal session termination. \\
\textbf{Steps}:
\begin{enumerate}
    \item Allow SOC to reach target OR manually stop the EV.
    \item EV sends `SessionStopReq`.
\end{enumerate}
\textbf{Expected Result}:
\begin{itemize}
    \item EVSE initiates Welding Detection.
    \item Contactors open (Voltage returns to 0V).
    \item EVSE returns to `Wait` state.
\end{itemize}

\subsection{TC-06: Safety/Emergency Stop}
\textbf{Objective}: Verify immediate shutdown upon fault or unplug. \\
\textbf{Steps}:
\begin{enumerate}
    \item During `Charging` state, physically disconnect the cable (CP line open).
\end{enumerate}
\textbf{Expected Result}:
\begin{itemize}
    \item EVSE immediately detects `CP State A`.
    \item State transitions to `Stop` or `Faulted`.
    \item Hardware output is disabled (< 20ms).
\end{itemize}

\chapter{OCPP 2.0.1 Protocol Details}
\section{Overview}
OCPP 2.0.1 is the latest version of the Open Charge Point Protocol, enabling communication between the EVSE and the Charging Station Management System (CSMS). Unlike previous SOAP-based versions, it relies heavily on JSON over WebSockets for efficient, real-time data exchange. Key improvements include enhanced security, Plug \& Charge support, and device management.
