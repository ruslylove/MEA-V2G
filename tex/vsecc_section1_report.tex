\subsection*{Test Setup}
The vSECC connects directly to the MEA CSMS at
\texttt{wss://ocpp.measandbox.com:2930/EV/Srv/JSON/1.6/rddQC4000001}
over TLS (Security Profile 1) with no intermediate proxy.
The test PC observes OCPP traffic via the vSECC's \texttt{GET /api/logging/files/ocpplib.log}
REST endpoint (TRACE-level log containing raw \texttt{>>>} sent and \texttt{<<<} received frames)
and via MQTT at \texttt{192.168.1.166:1883} (topic \texttt{vsecc/\#}).
Internet access for the vSECC is provided by the test PC acting as a NAT gateway
(nftables masquerade, \texttt{net.ipv4.ip\_forward=1}).

\section{Notes on Warnings}

\subsection*{MEA sandbox limitations (items 1.3--1.7)}
The MEA sandbox REST API does not expose the \texttt{/remote/triggerMessage} endpoint
(HTTP~404 for all casing variants tested).
TriggerMessage requires the CSMS to initiate the command; it cannot be triggered
via the MEA REST API alone.
Items 1.4, 1.6, and 1.8 depend on TriggerMessage and are therefore also WARN.

\subsection*{ChangeAvailability (items 1.13--1.16)}
The MEA sandbox \texttt{/remote/changeAvailability} endpoint returns HTTP~404.
ChangeAvailability was instead issued via the vSECC's MQTT
\texttt{vsecc/connector/1/status/set\_availability} topic.
The resulting OCPP \texttt{StatusNotification} frames
(\texttt{status=Unavailable} and \texttt{status=Available}) were observed in the
vSECC's \texttt{ocpplib.log} confirming the transitions reached the CSMS.
Items 1.13--1.16 are therefore \textbf{PASS}.

\subsection*{GetConfiguration (item 1.9)}
The MEA CSMS processes \texttt{GetConfiguration} asynchronously and returns HTTP~200
with an empty body.
The \texttt{ocpplib.log} was polled for the vSECC's CALLRESULT containing
\texttt{configurationKey} but no frame was captured within the 4\,s poll window.
The vSECC does accept \texttt{ChangeConfiguration} for all standard keys
(items 1.10--1.12 and 1.21 all PASS), confirming correct key handling.

\subsection*{Boot StatusNotification (item 1.2)}
The \texttt{VseccLog} baseline is recorded after the vSECC has already established
its OCPP session, so the boot-time \texttt{StatusNotification} falls outside the
capture window.
A vSECC restart at test start would resolve this; deferred to a dedicated reboot test.

\subsection*{DiagnosticsStatus / FirmwareStatus (items 1.18, 1.20)}
Both items are discretionary.
The vSECC does not send \texttt{DiagnosticsStatusNotification} or
\texttt{FirmwareStatusNotification} within the 6\,s observation window in this
environment (no real FTP server is reachable at the configured test URL).
